# TA-11 — Animation, Camera, VFX, and Presentation-State Integration

> **Status:** Architecture Complete  
> **Authority:** Animation playback/state selection, gameplay-vs-presentation transform boundary, camera effects, VFX/decals presentation triggers, committed-event synchronization, interpolation, and presentation-only state lifetime

## 1. Purpose

TA-4 already owns rendering and TA-10 owns imported animation/content assets. TA-11 must define how gameplay state selects animation, camera, VFX, and other presentation responses without allowing presentation timelines or animation notifies to become gameplay authority.

## 2. Presentation State Resolver

The baseline uses project-owned presentation resolvers that map immutable gameplay/read state plus committed presentation events into:

- animation state/clip requests;
- camera presentation state;
- VFX/particle/decal requests;
- optional audio/haptic presentation cues;
- UI/HUD presentation state.

Resolvers never mutate authoritative gameplay state.

## 3. Animation Runtime Boundary

Imported TA-10 skeleton/animation clips are presentation resources.

Active actors can expose an `AnimationPresentationState` containing conceptually:

- skeleton/rig ContentId;
- locomotion/action state;
- current clip/state identity;
- normalized playback phase;
- blend state;
- additive layers;
- look/aim presentation parameters;
- source actor/runtime generation.

The renderer/animation runtime consumes this state; gameplay does not read back bone transforms as ordinary authority.

## 4. Gameplay Transform Authority

Player/NPC/robot/ship authoritative transforms remain TA-5/TA-7 simulation state.

Baseline locomotion animation is **in-place**.

Animation/root motion does not move the authoritative actor unless a later explicitly authored mechanic defines a tightly scoped root-motion transaction under its owning gameplay system.

No generic animation-driven movement authority exists.

## 5. Character Locomotion Presentation

Locomotion animation selects/blends from actual runtime state such as:

- grounded/airborne;
- speed/direction;
- crouch/sprint;
- jump/fall/land;
- Zero-G/Magnetic-Boot state where authored;
- weapon/tool pose;
- injury/status presentation state.

An animation clip cannot create a movement capability the CharacterMotor does not have.

## 6. Action Animation

Weapon, interaction, repair, hacking, tool, reload, docking/console and similar animations synchronize to authoritative action state.

Presentation may begin when the action starts and update across stages, but final completion animation/cue cannot precede the committed state transition it represents.

## 7. Reload Boundary

Reload animation does not transfer ammunition.

The weapon/reload domain owns transfer stages/commit. Animation reflects the stage and can align presentation markers, but interruption/commit follows gameplay authority.

## 8. Melee/Attack Boundary

Attack animation does not perform hit resolution merely because a swing frame is reached.

The owning weapon/combat system schedules the authoritative attack/hit window and physics query under GDS/TA-5/TA-7 rules.

Animation presentation can be synchronized to that window through shared action phase data.

## 9. Animation Markers

Clip markers/notifies can request **presentation-only** events such as:

- footstep sample alignment;
- cloth/mechanical sound;
- dust puff;
- casing ejection visual;
- hand/contact pose cue;
- camera presentation accent where allowed.

They cannot directly:

- deal damage;
- transfer ammo/resources;
- complete objectives;
- open/lock doors;
- grant items;
- mutate persistent state.

## 10. Footstep Marker Boundary

Animation markers may align a footstep presentation sound/VFX with the visual foot plant.

AI hearing/gameplay sound authority is generated by locomotion/gameplay physical state, not by the renderer animation notify.

## 11. Animation Event Staleness

Animation/presentation events carry actor/runtime generation and action generation/correlation where relevant.

A marker from an interrupted/replaced action or destroyed actor is rejected.

## 12. Animation Interpolation

Render-frequency animation presentation can interpolate/blend between stable simulation snapshots.

Interpolation changes only presentation pose.

Authoritative movement/collision remains fixed-tick state.

## 13. Persistent Actor Reactivation

After scene activation/load, presentation state reconstructs from authoritative actor/action/status state.

The save does not need to serialize arbitrary internal blend-tree pointers or backend animation handles.

Where continuity matters, a small semantic playback phase/action state can be derived/stored by the owning runtime/save contract rather than serializing renderer objects.

## 14. Animation State Machine Scope

StarForge uses purpose-built typed presentation state machines for actor families rather than a general-purpose visual scripting animation graph requirement.

Shared facilities may support:

- state selection;
- crossfade;
- layered upper/lower body;
- additive pose;
- sync group;
- one-shot action overlay.

Gameplay behavior is not authored inside these state machines.

## 15. Camera Authority

TA-4 owns camera/view transforms. TA-11 presentation can apply camera effects such as:

- head bob;
- recoil viewpoint displacement;
- damage shake;
- landing/impact impulse;
- sprint/weapon FOV presentation;
- camera transition/cut;
- accessibility reductions.

These effects do not alter authoritative actor/weapon transforms or hit resolution unless the owning gameplay system separately changes them.

## 16. Camera Shake

Camera Shake supports 0–100% presentation scale with 0% fully supported.

At 0%, gameplay impacts/damage remain through HUD/audio/haptics/world state.

Camera shake cannot be used as the sole warning channel.

## 17. Head Bob

Head Bob supports 0–100% with 0% fully supported.

Disabling head bob does not change movement speed, step cadence, AI hearing, collision, or stamina/energy semantics.

## 18. Recoil Boundary

Mechanically authoritative recoil/spread/weapon aim displacement remains Combat/Weapon authority.

TA-11 camera recoil may visually reinforce the result but cannot remove or add mechanical shot deviation.

Accessibility can reduce presentation camera kick without silently changing weapon mechanics.

## 19. Cosmetic Weapon Sway

Purely cosmetic weapon sway is presentation and can be reduced.

Any actual aim/spread mechanic must be represented separately in gameplay state and cannot live only in a viewmodel animation.

## 20. FOV

First-person FOV uses the GDS accessibility target/default and TA-4 camera projection.

User FOV changes presentation projection within validated safe bounds and do not modify interaction/weapon ranges or physics query geometry.

ADS/zoom behavior uses owning weapon state plus camera presentation profile.

## 21. Motion Blur

TA-4 baseline has Motion Blur omitted/Off by default.

TA-11 does not introduce a gameplay dependency on motion blur. If added later, it remains presentation-only and disableable.

## 22. VFX Trigger Boundary

VFX requests originate from committed/validated presentation facts such as:

- weapon fired;
- projectile impact;
- shield hit;
- component damaged;
- fire/leak state;
- repair progress/completion;
- construction preview/commit;
- docking capture;
- objective/interaction feedback.

VFX cannot create the underlying state it depicts.

## 23. Persistent Environmental VFX

Persistent hazards/incidents such as fire, leak, electrical arc, anomaly or damaged machinery are represented from current owning-system Read Models.

If the scene/VFX unloads/reloads, the effect reconstructs from current incident state.

Destroying the particle emitter does not clear the fire/leak gameplay state.

## 24. One-Shot VFX

One-shot VFX from committed events use event correlation/generation so a render frame reload or repeated Read Model publication does not duplicate the effect.

Examples include muzzle flash, impact spark, shield flare, docking latch burst, transaction confirmation effect.

## 25. Decals

Decals are presentation resources tied to scene/content lifetime.

They may represent impacts/damage evidence, but gameplay damage/penetration state is not inferred from decal existence.

Persistent structural damage that must survive unload/load is owned by persistent gameplay state and can regenerate appropriate decals/mesh state.

## 26. Particle Authority

Particles cannot:

- deal damage because a sprite overlaps an actor;
- block collision/navigation;
- serve as objective identity;
- own a resource/item;
- alter atmosphere/fire state.

Gameplay hazards/projectiles remain separate TA-5/TA-7 state.

## 27. Reduced Effects

Reduced Effects/graphics tiers can lower decorative:

- particle counts;
- smoke density;
- debris;
- sparks;
- bloom/distortion;
- decal density where noncritical.

Gameplay-critical telegraphs/hazard boundaries remain above the critical-readability floor.

## 28. Photosensitivity

Presentation effect definitions expose safe alternatives for high-risk flash/pulse behavior.

Photosensitivity Safe Mode selects the safe variant/parameters without altering underlying gameplay incident timing or damage.

## 29. UI/World Presentation Synchronization

A committed event can fan out to multiple presentation consumers through one typed correlation:

`Committed Event -> HUD + Audio + VFX + Haptics + Animation presentation`.

Consumers may render at slightly different device/display latency, but they all refer to the same authoritative source result.

## 30. No Presentation-to-Gameplay Feedback Loop

Rendering an effect/animation/audio cue does not emit a gameplay success event back into the simulation.

If an animation/audio/VFX fails to load, the owning gameplay state remains exactly as committed.

## 31. Presentation Time

Presentation-only transitions/fades/blends may use monotonic non-gameplay Presentation Time.

Gameplay-coupled progress/timers always use authoritative Simulation Time/read state.

A UI fade or animation crossfade cannot delay/accelerate gameplay completion.

## 32. True Pause

When True Pause is active:

- gameplay-coupled animation/action progress freezes with simulation state;
- optional menu/UI presentation animation can continue with Presentation Time;
- camera gameplay effects freeze/fade according to pause policy;
- persistent hazard VFX display a static/paused state rather than advancing gameplay semantics;
- no new committed gameplay presentation event is generated.

## 33. Scene Transition

Scene-local presentation objects are generation-scoped.

On scene replacement:

- old actor animation/viewmodel/VFX instances retire;
- UI/system/music layers with broader lifetime can persist;
- destination presentation activates only after required content/read state is ready;
- stale async presentation results are rejected by SceneGeneration/ContentGeneration.

## 34. Floating Origin

Floating-origin rebase updates camera/emitter/VFX transforms coherently using OriginEpoch.

A rebase cannot create synthetic:

- camera impact;
- particle burst;
- footstep;
- collision flash;
- audio impact.

## 35. Viewmodel vs World Model

First-person weapon/tool viewmodel presentation can use a camera-relative render representation distinct from the authoritative/world physical item representation.

The viewmodel:

- references the same equipped item/weapon state;
- cannot fire independently;
- cannot own ammo;
- cannot define hit origin/range except through explicit weapon/camera gameplay contracts;
- can use presentation-only pose/FOV clipping solutions.

## 36. Third-Person/Ship Presentation

Ship chase camera, cockpit camera and first-person modes can choose different presentation animation/audio/VFX composition while preserving the same physical ship state and capabilities.

Camera mode cannot create different weapon hit physics unless the owning GDS explicitly defines a weapon mode difference independent of camera.

## 37. Interaction Highlight/VFX

Interactable highlight/outline uses eligible InteractionFocus/knowledge state.

Presentation cannot outline through walls or expose undiscovered targets unless accessibility/telemetry rules explicitly permit that already-known target.

## 38. Developer Diagnostics

Development tooling exposes:

- current animation states/clips/blends;
- action/commit correlation;
- rejected stale notifies;
- camera effect stack and accessibility scaling;
- active VFX sources/event IDs;
- persistent vs one-shot effect ownership;
- presentation-time vs Simulation-Time sources;
- scene/content generation tags.

## 39. Validation Requirements

Tests must verify:

- animation notify cannot damage/grant/complete gameplay;
- reload presentation cannot transfer ammo;
- root motion is not generic movement authority;
- camera shake/head bob 0% leaves gameplay identical;
- viewmodel failure does not alter weapon state;
- VFX reload cannot clear/recreate persistent gameplay incident;
- one committed event produces at most one correlated one-shot presentation per consumer;
- stale scene/action marker is rejected;
- floating-origin rebase creates no presentation impact event;
- Reduced Effects preserves critical telegraphs/readability.

## 40. Explicit Non-Goals

No baseline requirement for:

- general-purpose animation scripting/graph editor;
- animation-driven gameplay authority;
- particle collision as damage authority;
- renderer/VFX state serialized as persistent gameplay;
- camera shake as required feedback;
- viewmodel as inventory/weapon owner;
- presentation event callbacks that commit gameplay.

## 41. Dependencies

Depends on TA-2 events/read models, TA-3 scene/origin, TA-4 renderer/camera/VFX, TA-5/TA-7 gameplay transforms/combat/actions, TA-10 animation/assets, TA-11 HUD/audio/accessibility, and GDS Interaction/VFX/HUD/Accessibility.

## 42. Open Questions

None in the animation/camera/VFX/presentation integration architecture.
