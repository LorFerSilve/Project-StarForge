# TA-9 — Strategic State-Machine Runtime Integration, Debugging, and Validation

> **Status:** Architecture Complete  
> **Authority:** Ordering of Mission/Raid/DynamicEvent strategic work relative to the TA-7/TA-8 runtime tick, strategic deadline processing, committed-fact ingestion, consequence batching, asynchronous-generation boundaries, read-model publication, and TA-9 debug/validation requirements

## 1. Purpose

Mission, Raid, DefenseEvent, DynamicEvent, recovery, and finale state machines must react to local gameplay without making callback order, worker completion, UI timing, or strategic scheduler cadence authoritative.

TA-9 therefore defines one integration contract between:

- TA-7/TA-8 active-local fixed tick;
- TA-6 Horizon chronological scheduler;
- Mission/Objective state;
- Raid/Defense state;
- Dynamic Event strategic scheduling;
- communication/recovery/finale consequences.

## 2. Two Scheduling Scales

TA-9 uses:

1. **Local fixed-tick integration** for facts generated by the active SceneInstance at 60 Hz;
2. **Strategic deadline/event scheduling** for offers, travel/reinforcement ETA, Recovery Transit, event expiration/cooldowns, target recovery, and off-screen Horizon defense.

Both use the same global Simulation Time.

A strategic subsystem need not run a full update every 60 Hz, but any deadline crossed during an advance must be processed chronologically before later consequences are assumed.

## 3. Local Runtime Integration

TA-8's active-runtime order is refined as follows:

```text
1.  Tick Begin / Stable State Latch
2.  Apply normalized player/external intents
3.  Validate activation/spawn/despawn requests
4.  Process due local action/status deadlines
5.  Consume validated async AI/navigation results
6.  Ingest currently delivered perception/shared knowledge
7.  Run due AI decisions
8.  Build player/AI movement, weapon, interaction intents
9.  Pre-physics gameplay queries / kinematic targets
10. TA-5 Physics Step
11. Normalize contacts/overlaps/projectile/trigger facts
12. Resolve movement/support/physical state
13. Generate/update perception facts
14. Resolve Combat/interaction results
15. Commit immediate owning-domain gameplay consequences
16. Reflect committed consequences into active runtime
17. Build TA-9 mission/objective/raid fact batch from committed outcomes
18. Evaluate due objective/raid/defense transitions
19. Prepare/commit valid Mission/Raid/strategic consequence transitions
20. Queue resulting AI/mission/communication interrupts
21. Actor/object lifecycle transitions
22. Deferred runtime structural mutations
23. Deferred physics/navigation mutations
24. Stable Simulation Boundary
25. Publish immutable gameplay/mission/AI/render/UI/audio read snapshots
26. Tick End
```

TA-9 does not move physics/combat consequences earlier; it consumes **committed** results afterward.

## 4. Committed Fact Batch

The local tick produces a typed `StrategicGameplayFactBatch` for TA-9 containing only facts that have reached their owning-domain commit point.

Examples:

- target Destroyed/Disabled/Captured;
- scan evidence committed;
- resource ownership/security changed;
- protected actor Boarded;
- system repaired/compromised;
- extraction point physical eligibility changed;
- world/door/access state changed;
- player incapacitation/defeat committed.

Raw collision callbacks, uncommitted UI interactions, and speculative AI intent are excluded.

## 5. Fact Ordering

Facts carry:

- source tick;
- source domain;
- EventSequence/TransactionId where applicable;
- stable source identity.

TA-9 consumes them in explicit semantic/domain ordering with stable identity fallback.

Hash-map order and callback arrival order never choose which objective/branch/outcome commits first.

## 6. Objective Evaluation Phase

Objective predicates may inspect:

- current committed fact batch;
- immutable owning-domain state at the current revision;
- existing ObjectiveRecord state.

They produce transition proposals only.

All valid proposals are deterministically sorted and then committed through MissionStore transactions.

## 7. Cascading Objective Transitions

A committed objective can unlock/cancel dependent objectives or satisfy mission success/failure.

Cascades execute to a deterministic fixed point within a bounded mission transition pass for that tick.

A content-validation invariant prohibits cycles, so the resolver cannot oscillate forever.

If a downstream transition requires a separate cross-domain consequence, it is prepared after the upstream objective commit and still before snapshot publication when safe; otherwise it is queued for the next deterministic strategic boundary.

## 8. Raid / Defense Phase Evaluation

Raid phase and escalation/DefenseEvent transitions consume committed objective/system/perception/escalation facts after the owning lower-level systems settle.

Examples:

- breach state committed -> access phase can advance;
- reinforcement call committed -> escalation can enter ReinforcementsEnRoute;
- attackers physically gone -> defense can enter Recovery;
- hostile extraction committed -> defense objective can resolve.

A phase enum never anticipates an action that has not committed.

## 9. Strategic Scheduler Boundary

The `StrategicEventScheduler` processes all deadlines at or before the current Simulation Time in chronological order.

Candidate boundaries include:

- Dynamic Event evaluation;
- Offered event expiration;
- event cooldown/grace change;
- strategic communication delay delivery;
- Recovery Transit arrival/revalidation;
- reinforcement travel/arrival;
- raid-target recovery step;
- off-screen DefenseEvent engagement boundary;
- authored strategic timer.

For equal timestamps, explicit category priority plus stable typed ID/order is used.

## 10. Chronological Advance

When strategic simulation advances over a large interval:

1. find earliest due boundary `Tb`;
2. advance continuous/coarse participant systems only to `Tb`;
3. commit all causal facts at `Tb` in deterministic order;
4. rebuild affected eligibility/routes/state;
5. schedule newly caused boundaries;
6. repeat until target Simulation Time.

The scheduler cannot skip a reinforcement arrival, event expiration, station failure, or communication delivery and then pretend later state existed earlier.

## 11. Horizon Off-Screen Coordination

While the player is away:

- TA-6 StationSimulationScheduler and TA-9 Defense/DynamicEvent scheduler share chronological Simulation-Time boundaries;
- each scheduler exposes its next relevant deadline;
- the session-level strategic coordinator chooses the earliest boundary;
- resulting station/raid/event facts commit before computing the next horizon.

This prevents a coarse DefenseEvent step from firing through a power/ammo failure TA-6 says occurred earlier.

## 12. Active-Horizon Transition

When TA-3 stages Horizon during an ongoing DefenseEvent:

- strategic/off-screen state advances exactly to the context-transition commit time;
- no further off-screen engagement step is processed beyond that time;
- current event/attacker/crew/robot state is activated;
- high-frequency TA-7/8 runtime takes over leased facets;
- persistent DefenseEvent/TA-6 stores remain authority.

The reverse handoff uses the same stable-boundary discipline.

## 13. Async Procedural Generation

Mission/Event procedural candidate building may use workers only on immutable snapshots.

A result carries:

- source scheduler generation/ordinal;
- source revisions;
- content/generator version;
- candidate ordinal;
- JobId.

Main-thread consumption validates freshness and chooses candidates by semantic candidate order, not job completion order.

No worker allocates persistent IDs or commits Mission/DynamicEvent state.

## 14. No Long-Lived Open Transaction

Strategic timers can span hours of Simulation Time, but no TA-2 transaction remains open across ticks/deadlines.

Persistent records represent in-progress states such as:

- EnRoute;
- Calling;
- Responding;
- RecoveryTransit;
- Scheduled.

Each transition is its own prepared/committed transaction.

## 15. Same-Time Cross-System Conflicts

Potential conflicts such as:

- event expires while player acceptance command arrives;
- reinforcement source is destroyed at departure deadline;
- Horizon recovery point becomes unsafe exactly at player arrival;
- final mission choice intent arrives in the same tick as terminal defeat

use explicit transaction/precondition ordering.

Earlier valid commit changes revisions/preconditions; later conflicting operation must fail/re-evaluate rather than merging heuristically.

## 16. Finale Ordering

FinalChoiceIntent is evaluated only after current local combat/objective facts for the tick commit.

If the player becomes terminally unable to complete Phase D before choice commit, the FinalResolution transaction cannot ignore that state merely because UI input occurred earlier in the render frame.

Once FinalResolution commits, later same-tick consequences observe the persisted ending choice and cannot replace it.

## 17. Read-Model Publication

Mission log, objective HUD, event notifications, raid status, remote Horizon telemetry, recovery summary, and postgame state are published as immutable revisioned read models only after authoritative transitions for the boundary settle.

Read models apply knowledge boundaries:

- hidden objectives stay hidden;
- undiscovered hazards stay unknown;
- undelivered Dynamic Events do not appear;
- unknown reinforcement source/ETA does not leak;
- remote Horizon state is limited to delivered telemetry fidelity.

## 18. Presentation Event Emission

Audio/UI/VFX presentation signals are emitted from committed transitions, for example:

- ObjectiveCompleted;
- MissionFailed;
- ReinforcementDetected;
- HorizonAttackAlertDelivered;
- RecoveryTransitStarted;
- FinaleChoiceCommitted.

Presentation events are not authority and replay suppression uses source transition identity/sequence where necessary.

## 19. Save Snapshot Readiness

TA-9 exposes `IsStrategicStateStableForSnapshot()` or equivalent invariants to the TA-2/TA-12 save architecture.

A Stable Save Boundary requires:

- no partially applied prepared consequence commit;
- all due same-boundary mission/objective cascades settled;
- external deployed-slot references valid;
- DynamicEvent Mission/Defense links valid;
- physical ownership transfers settled;
- finale transaction either entirely pre-commit or post-commit.

Worker jobs may still exist because their results are advisory/recomputable, provided no save DTO depends on an uncommitted worker result.

## 20. Debug Tooling Requirements

Dear ImGui development tools should provide read-only inspectors for:

- MissionStore and MissionInstance history;
- objective DAG/state/predicate sources;
- generated mission seed/package/rejection diagnostics;
- Raid phase + escalation + target state;
- reinforcement call/source/ETA;
- DefenseEvent active/off-screen state;
- DynamicEvent scheduler cursors/cooldowns/grace;
- communication/message timeline;
- Recovery Transit;
- strategic consequence batches/TransactionIds;
- finale eligibility/prepared/committed state.

## 21. Timeline Debugger

A development strategic timeline view should correlate by Simulation Time:

- committed transactions;
- objective transitions;
- mission lifecycle;
- DynamicEvent creation/expiry;
- reinforcement call/departure/arrival;
- DefenseEvent phases;
- communication delivery;
- recovery transit;
- finale choice.

This is diagnostic history, not gameplay persistence authority unless the owning domain separately requires those records.

## 22. Determinism Diagnostics

Development builds can hash selected normalized TA-9 state at Stable Simulation Boundaries to compare deterministic test runs.

Hash input must use canonical deterministic ordering and exclude:

- pointers;
- runtime handles when identity-independent;
- wall-clock timestamps;
- worker completion timing;
- render-only state.

## 23. Headless Execution

All TA-9 state machines, procedural validation, off-screen DefenseEvent simulation, DynamicEvent scheduling, recovery, communication delivery logic, and finale transactions must execute headlessly without OpenGL/audio/UI.

This is required for TA-14 CI/regression testing.

## 24. Failure Diagnostics

Invariant failures report typed IDs and revisions, for example:

- MissionId / MissionInstanceId;
- ObjectiveId;
- RaidId;
- DefenseEventId;
- DynamicEventId;
- TransactionId;
- Simulation Time;
- relevant source/target revisions.

The runtime does not silently repair contradictory authoritative ownership/state except through explicit validated recovery/migration logic.

## 25. Performance Boundary

TA-9 defines semantic correctness, not numeric budgets.

TA-13 later sets:

- mission/objective evaluation budgets;
- DynamicEvent evaluation cadence/budget;
- off-screen defense engagement granularity;
- procedural-generation worker budget;
- strategic backlog limits.

A performance budget may defer nonurgent work but cannot skip already-due mandatory semantic deadlines.

## 26. Test Categories

TA-14 implementation must include headless deterministic tests for at least:

- mission lifecycle/deployment exclusivity;
- objective DAG/exactly-once transitions;
- procedural no-reroll generation;
- raid target persistence;
- reinforcement pre/post-call-commit behavior;
- active/off-screen DefenseEvent equivalence at semantic boundaries;
- physical hostile theft/extraction;
- DynamicEvent concurrency/grace/expiry;
- communication knowledge separation;
- Recovery Transit anti-teleport behavior;
- cross-domain consequence atomicity;
- finale exactly-once choice;
- Stable Save Boundary invariants.

## 27. Explicit Non-Goals

No strategic mutation from render/UI callbacks, worker-race mission outcomes, variable-real-time timers, one global untyped event queue, open transaction across multiple ticks, or debug inspector acting as hidden gameplay authority.

## 28. Dependencies

Depends on `61`–`68`, TA-1 Simulation Time, TA-2 transactions/save boundary/read models, TA-6 chronological Horizon scheduler, TA-7 runtime phases, TA-8 AI/navigation scheduling, and all corresponding Design Complete Mission/Raid/DynamicEvent/Recovery/Finale rules.
